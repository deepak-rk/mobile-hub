# Mobile Hub — Lessons Learned

A running log of real mistakes made in this repo (bugs shipped, wrong assumptions, scope missed) and what changed as a result. Not a design-decision log — that's `docs/architecture-blueprint.md` and ADRs. Not a "things to watch out for in general" list — that's the "Lessons carried in from the reference architecture" section of root `CLAUDE.md`. This file is specific and retrospective: *we actually did X, here's what it cost, here's the rule now.*

Newest first. See root `CLAUDE.md` § Self-review for when to add an entry.

---

## 2026-11-22

**A literal NUL byte was committed into source and nobody noticed for a commit.** `InstallDialog.tsx`'s key separator was meant to be the escape `\u0000`, but a shell-driven edit turned the escape into an actual NUL character. It still worked at runtime, so tests passed — but git began treating the file as binary (`Bin 6545 -> 7115 bytes` in the diff), which hides every later change to it from review. The same mangling happened again this session in a heredoc-fed script and was caught only by `od -c`. **Rules now**: (1) write backslash escapes in source with the Edit/Write tools, not through a shell heredoc or `sed`; (2) a `Bin` line for a `.ts/.tsx` file in `git diff --stat` is a bug, stop and fix it before committing; (3) one shared key helper per identity (`features/devices/lib/deviceKey.ts`, backend `deviceKey()` in `install-runs.service.ts`) instead of a hand-written separator per file.

## 2026-11-21

**An information-dense source was skimmed, summarised, and turned into a plan — and the plan was wrong in specifics while sounding right in general.** The input was six photographed A3 pages of a production farm's architecture, four of them upside down, in small type. They were read once at half resolution and a plan was written from the gist. The user pushed back ("sounds like you skimmed"). A second pass — every page cut into native-resolution tiles, rotated, transcribed verbatim, then each lesson checked against this repo's actual code — found that rev 1 had (a) stated a false fact about this code ("runner env is ad-hoc"; it was not), (b) presented 13 farm lessons as future advice when **13 were live bugs here**, two of them in fixes made the previous week (the `/wd/hub` path resolved then discarded; the "never fail queued" choice the farm's data contradicted), and (c) missed whole categories: outcome-overwrite writers, cache atomicity, zero-test detection, run timeouts, emulator boot gating. **Rules now**: (1) a dense or awkward source (photos, rotated pages, small type) gets a transcription pass *before* any analysis — read at native resolution, tile it, write it down verbatim; summarising while reading is where the detail is lost. (2) Every lesson taken from another system is checked against this repo's **code**, one by one, and ends in one of three states: already handled (cite the line), bug here (fix it), or gap (plan it) — never left as "advice to adopt". (3) A plan's claims about the current code are verified by grep before they are written; "X is ad-hoc" is a factual claim. (4) When another system's data contradicts a choice made here, revisit the choice on the record rather than defend it.

## 2026-09-23 (later)

**An authorization gap that was invisible to every check except comparing routes against each other.** The three device-lock routes asked only `app.authenticate` — "are you signed in?" — with no role requirement, while all eleven other human-facing mutating routes required `requireRole(...)`. So a read-only `viewer` could lock any device and renew that lock indefinitely; a locked device cannot start a queued execution run, which makes it a denial-of-service available to the *least*-privileged role. The frontend had the identical gap, and `LockControls.tsx`'s own doc comment stated the rule it was violating ("actions are hidden rather than disabled when the caller can't perform them, so nobody clicks a button that can only 401") while checking only signed-in and admin-force-unlock, never the base action.

Nothing local could have caught this: each file is internally consistent, both sides agree with each other, types pass, and the comment describes correct intent. It only appeared when every mutating route was listed next to its guard and the odd ones out were visibly three. **Rule now**: authorization is a property of the *set* of routes, not of any one route — audit it by enumerating every mutating endpoint with its guard in one table and looking for the outlier, not by reading handlers one at a time. And the related trap: **frontend and backend agreeing is not evidence either is right.** Both were wrong here in exactly the same way, which is the expected outcome when one was written from the other rather than from the policy. The test to write is the one that pins the *whole set* — the catch-all here fails any mutating device route left on authentication alone, which is the shape of the bug rather than one instance of it.

## 2026-09-23

**The fifth instance of "in-flight state with no owner to finish it" — and the one where the obvious fix would have been a bug.** An agent that died mid-install left its target at `downloading`/`transferring`/`installing` permanently: `getPendingInstallsForMachine` hands the agent only `queued` targets, so a started-then-abandoned one was never re-picked-up, and no hub-side sweep ever failed it. The install never completed, never errored, and `getActiveInstallUdids` kept counting it — so the device displayed an "Installing" badge forever *while simultaneously being marked offline* by the stale-host sweep. Two contradictory facts about one device, both rendered.

The interesting part is that the pattern established four times earlier this session — "add a boot-time reconciler, like `recoverOrphanedRuns`" — would have been **wrong** here. Execution runs, builds and stream sessions are all hub-owned: if the hub restarted, their work definitively died with it, so anything still marked live is stale by definition. An install target is *agent*-owned. A hub restart leaves it genuinely still running on a healthy agent, and failing it at boot would both lie and invite a duplicate install onto a real device. The correct trigger is the agent's own absence, which `markStaleHostsOffline` already detects and already acts on (it marks devices offline and releases locks) — it just never cleaned up the agent's in-flight install work. **Rule now**: before reaching for a boot-time reconciler, ask *whose process was doing this work*. "Mine, and I just restarted" licenses a startup sweep; "someone else's, over a network" does not — that needs a liveness signal about **them**, and the sweep that already watches their heartbeat is where it belongs. And the narrower trap inside it: `queued` looks in-flight (it is, for the badge) but is the one status that genuinely self-heals, so sweeping it would turn a recoverable wait into a permanent error — the correct set to fail was "in-flight **minus** the resumable one", not all of it.

## 2026-09-22 (final)

**Two more cleanup functions were written, correct, documented with their own contract — and called from nowhere at all.** `recoverOrphanedBuilds` says *"Call once at server startup, before accepting traffic — the same contract as execution's `recoverOrphanedRuns`."* Nothing called it. A restart mid-download left the `Build` row at `downloading`, which holds the `one_inflight_fetch_per_version` partial unique index entry and so permanently blocked every future fetch of that version — the function's own doc comment describes this exact consequence, one paragraph above the code that would have prevented it. `shutdownLocalAppiumServers` says *"called on agent shutdown so nothing outlives the process that owns it."* Also called from nowhere — while `streamRelay.shutdown()`, three lines away in the same `stop()`, was correctly wired for identical reasons. Every agent restart orphaned one live Appium process per device.

**Rule now**: a function's doc comment asserting *when it is called* is a claim about a call site that may not exist — grep for the caller before trusting it, especially for anything named `recover*`/`shutdown*`/`cleanup*`, whose whole purpose is to run on a path nobody exercises by hand. The cheap systematic version, which is what actually found these two: list every exported function with no reference outside its own file and its tests. Most hits are legitimately test-exported helpers; the ones that are lifecycle hooks are bugs, every time. This is the third and fourth instance of this class in one session — see the `setInterval` entry below (scheduled but never reached its first tick) and the `machineId` entry (parameter added, no caller passed it). The common shape across all four: **the work was done, and only the last wire was missing, so every artifact that a reviewer would check — the function, the test, the doc, the comment — looked complete.**

## 2026-09-22 (latest)

**A single WebSocket connection could terminate the entire backend, and the safe version of the exact same line was sitting 25 lines above the unsafe one.** A close reason must fit in 123 bytes (RFC 6455); `ws` throws a `RangeError` rather than truncating. `streaming.routes.ts` had two `socket.close()` calls with dynamic reasons — one wrote `message.slice(0, 120)` (someone clearly knew), the other passed `err.message` verbatim. The capacity messages are ~170 bytes, so a viewer attaching to a device on a host already at its capture cap threw *inside the handler's own catch block*, which made it an unhandled rejection in a fire-and-forget async IIFE, which killed the process. Confirmed live: the hub stopped answering on `:3000` at all, for everyone, triggered by one ordinary user hitting an ordinary "host is busy" condition. **Rules now**: (1) when a constraint is handled at one call site, grep for the other call sites of that same API in the same file before assuming it's handled — a local fix is evidence the author knew about the hazard, not evidence they covered it everywhere; (2) `.slice(n)` is characters, a protocol limit is bytes — the "safe" call site was also latently wrong for any multi-byte text; (3) a fire-and-forget `void (async () => {...})()` handler needs a terminal `.catch()`, because a throw from inside its own `catch` block escapes everything and Node's default for an unhandled rejection is to exit. This codebase already applied rule 3 in `execution.service.ts` ("a last-resort net so a bug there can't become an unhandled rejection") — the pattern existed and simply hadn't been applied here.

**The leak that made it reachable:** a capture's liveness lived in an in-memory `Map` that dies with the process, while its `StreamSession` row survived — and nothing reconciled them at boot. Every restart-while-streaming left a row permanently claiming `active`, and `assertCapacity` counts exactly those rows against `ANDROID_STREAM_CAP` (default 3). Three such restarts and the host refuses every new stream forever, citing load that isn't there. Found by noticing the hosts API reported `streams: 1` when nothing was streaming, on a row still naming a viewer id belonging to a *deleted* user. The reference review had flagged this precise class ("a registry of live child processes kept only in a process-memory Map is invalidated by any restart") and `recoverOrphanedRuns()` already existed for execution — streaming just never got the equivalent. **Rule now**: any durable row that mirrors in-process state needs a boot-time reconciler, and the test for whether you need one is simply "does this row outlive the process that made it true?" Where one such reconciler exists, that is a checklist of one — go find the other mirrors.

## 2026-09-22 (later still)

**Three scheduled jobs were correctly written, correctly registered, and never actually ran.** `computeDailyAggregates` (hourly), `runBuildGc` (hourly) and `computeWeeklyAggregates` (daily) were each wired up with `setInterval` in `server.ts` — which only fires *after* a full period elapses. Every restart puts the first tick back another full period, so any job whose interval is longer than the process's typical uptime never executes at all. In development, where the backend restarts many times an hour, the two hourly jobs had likely never run once; the weekly one would never run in any deployment that ships more than daily. Nothing failed loudly — the analytics page simply read "Daily rollups… recomputed hourly" above data that was **21 hours stale**, with the current day's runs missing and the trend chart drawing nothing. Confirmed by deleting the current day's aggregate, restarting, and watching the server rebuild it unprompted once a boot-time run was added. **Rule now**: `setInterval(fn, period)` is only a complete schedule when `period` is much shorter than expected uptime. For anything hourly or slower, run it once at startup too (`runNowAndEvery` in `server.ts` now enforces this for every periodic job in the file, including the short sweeps, so there is one rule instead of a judgement call per job). And the detection lesson: this class of bug produces no error, no failing test, and no log line — only a number on a screen that is quietly older than its own label claims. **A UI element that states its own freshness ("recomputed hourly", "updated every N minutes") is a testable assertion — check it against reality when looking at the page, rather than reading past it.**

## 2026-09-22 (later)

**A fix written for a gap, and the new feature that gap belonged to, shipped the same day — and the fix didn't cover the new feature's own path.** `closeActiveSessions()` was built 2026-09-21 to close orphaned WebDriver sessions, and `ensureRemoteAppiumServer()` (agent-hosted Appium, for devices on a remote host) was built the same day in the same module. But `closeActiveSessions` built its target endpoint from `config.appium.host` + `device.appiumPort` unconditionally — the *hub-local* pair. On the remote path `appiumPort` is never assigned at all, so the function hit its `if (!device.appiumPort) return;` guard and silently did nothing, leaking precisely the session it existed to close. Confirmed by reverting the fix against a new regression test: **zero HTTP calls** for a remote device. Both the traceability doc and the code comments described the cleanup as done, because on the hub-local path it genuinely was — and that's the only path anything live-exercised. **Rule now**: when a feature adds a second code path for something that already had one (hub-local vs agent-local, here), every *existing* helper that reads the old path's fields is a candidate bug, not just the new path's own code. Grep for the old path's field names (`appiumPort`) and check each read against "does this also need the new path's field?" — a new path doesn't announce which existing readers it silently broke, and a feature flag defaulting to `false` means no test or live run will surface it either.

**And the same machineId-scoping bug that was found and fixed in `devices.service.ts` was still sitting, unswept, in `execution.service.ts` — seven call sites of it.** The 2026-09-21 entry below records adding an optional `machineId` to `getDevice`/`acquireLock`/`releaseLock` so a device is addressed by the compound key its own unique index is built on. That fix added the *capability*; the execution module — the single heaviest consumer of all three functions — never passed it, at any of its seven call sites, despite having `machineId` in scope at every one (`input.machineId`, `run.machineId`, `candidate.machineId`). So a run on host A could lock, read, or release host B's same-udid device. **Rule now**: "made the function accept a disambiguator" and "callers pass it" are two separate pieces of work, and finishing the first while calling the item done is how a fix becomes a false sense of safety. When a signature gains an optional correctness parameter, grep every call site in the same change and either pass it or record why not — an optional parameter that nobody passes is indistinguishable from not having fixed anything.

## 2026-09-22

**A correctly-built feature made live-verifying a *different* feature look broken, and the false alarm cost real time before the actual cause (a testing-environment quirk, not an app bug) was found.** After shipping tab-visibility-pause for streaming (`useDeviceStream.ts`'s `usePageVisible()`, gating the WS `url` on `document.visibilityState === 'visible'`), a live-browser check of an unrelated, already-verified feature (JPEG compression) got stuck at "Waiting for the first frame…" with zero WS connection ever reaching the backend. Nearly mistaken for a JPEG-compression regression. The real cause, confirmed by reading `document.visibilityState`/`document.hidden`/`document.hasFocus()` directly in the page via `javascript_tool`: Claude's own Chrome browser-automation tool reports the CDP-controlled tab's `visibilityState` as `"hidden"` even when it is the sole, selected tab and `hasFocus()` is `true` — a real limitation of automated/CDP-driven browser tooling generally, not a bug in this repo's code. The visibility-pause feature was working exactly as designed; it correctly refused to stream to a page the browser itself reports as not visible. **Rule now**: any live-browser verification of a stream/capture feature through Claude's own browser tool must account for this — if a WS-gated feature seems to never connect, check `document.visibilityState` in the page directly before assuming the feature under test is broken, especially right after shipping a visibility-gated change elsewhere in the same area. A raw capture test (bypassing the browser, calling the capture source directly) remains the more reliable verification path for anything visibility-gated.

## 2026-09-21 (later)

**Every real execution run had been failing at the `installing` stage for an unknown length of time, and the cause was a Node.js *behavior change*, not a bug ever written in this repo.** Found only because a live-verification pass insisted on watching a real run to completion instead of trusting typecheck/lint/test (which all stayed green throughout, since nothing in the test suite spawns a real `.cmd` shim without mocking it). Recent Node versions refuse to `spawn()` a `.bat`/`.cmd` file directly at all — `EINVAL` — closing a command-injection class the old implicit shell-out behavior allowed. `common/process-supervisor.ts`'s own `resolveExecutable()` correctly found `npm.cmd` on disk; the failure was one layer up, in `spawn()` itself refusing to run what it found. Reproduced in total isolation (`npm --version` alone, no repo code involved) before writing a line of fix, which is what confirmed it wasn't anything specific to this codebase's resolution logic. Fixed with `shell: true`, scoped to only `.cmd`/`.bat` resolutions — and this **invalidated a comment in the same file** claiming `shell: true` "breaks cancellation," which turned out to be a stale POSIX-signal-delivery concern that never applied to this file's own Windows tree-kill mechanism (`taskkill /T /F` kills by PID, reaching the whole tree through a `cmd.exe` hop exactly the same as without one). **Rule now**: a doc comment recording *why* an approach was rejected is a claim about a point in time, not a permanent fact — when the environment underneath a piece of code changes (a Node upgrade, here), the original rejection reasoning needs re-checking, not just the code's current behavior. And more generally: a test suite that mocks the exact boundary where a platform's own behavior can shift (every process-spawning test here mocks or stubs the shape of the call, never spawns a real `.cmd`) will stay green through a regression that only a live run can catch — this is why `docs/architecture-blueprint.md`'s own "real processes, not mocks" testing philosophy for this specific module exists, and why the live-verification step of a task is not optional busywork once the automated checks pass.

**The same fix silently broke a second thing in a different module, discovered only because a parallel workstream happened to live-verify its own, unrelated feature against a real Appium spawn afterward.** Making `.cmd` spawns go through `shell: true` means they now go through `cmd.exe`, and `cmd.exe`'s own argument re-quoting stripped the double quotes out of Appium's inline JSON `--default-capabilities` argument — silently breaking Appium startup on every path that passes it, discovered only by an agent-locality feature's own live verification failing for a reason that had nothing to do with agent locality. **Rule now**: a fix to a shared, low-level primitive (`process-supervisor.ts` is used by every module that spawns anything) needs its blast radius checked across every caller that passes something more structured than a bare flag through `args` — a JSON string, a path with special characters, anything a shell's own reparsing could mangle — not just the one caller whose bug prompted the fix. This is the second time in this file a shared primitive's fix has had a non-obvious knock-on effect elsewhere (see the 2026-08-29 process-supervisor extraction entry) — worth treating "I just changed a primitive everything depends on" as its own trigger for "did I just verify every caller, not just the one I was looking at."

## 2026-09-21

**A documented architecture principle applied correctly at the schema layer had quietly stopped being applied one layer up — and the same exact mistake existed in two unrelated places in this codebase.** `device.model.ts`'s compound `{machineId, udid}` unique index is correct and has a comment explaining why (the same UDID can exist on different hosts — the normal case for emulators). But `devices.service.ts`'s `getDevice`/`acquireLock`/`releaseLock`/`renewLock`, and the public routes built on them, all query by `udid` alone — and, found independently in the same pass, `appium.service.ts`'s in-memory `servers` Map was also keyed by `udid` alone, despite `streaming.service.ts` right next to it having the correct compound-key pattern (`captureKey(machineId, deviceUdid, protocol)`) to copy. Both were invisible in a dev environment that only ever runs one real host — a UDID collision literally cannot occur with one machine — so nothing ever exercised the bug. Found only by comparing against a *different* real system's own fix log, which described hitting exactly this failure class (an in-use indicator keyed on UDID alone, misattributing state across two hosts) after they started running real multi-host deployments. **Rule now**: when a design principle is stated once ("machineId is first-class, not an afterthought") and correctly applied at the schema, that is not evidence it was applied everywhere the schema's data flows to — check every read/write path built on top of the schema, not just the schema itself, especially for anything a single-host dev environment structurally cannot exercise. A principle proven right at one layer earns re-checking at the next, not an assumption it already happened.

## 2026-09-05 (later)

**`scripts/start.mjs`/`stop.mjs` had never actually been run, and the reason had nothing to do with the scripts.** Both were built and typechecked weeks earlier but left as "built, not verified" in `docs/TODO.md` after an earlier session paused mid-verification. Trying it this session, `scripts/start.sh` (the *old* script, run out of habit) failed with `node: not found` — and so did every other `node`/`npm` command in a fresh shell on this machine. Root cause: `nvm4w`'s active-version symlink (`C:\nvm4w\nodejs`) pointed at a Node version that had since been uninstalled (only a newer one remained), so `node`/`npm` had silently vanished from PATH for *any* shell, not something wrong with this repo at all. Fixed with `nvm use <installed-version>`. **Rule now:** a `command not found` for a normally-always-present tool (node, npm, git) is worth checking as an environment/PATH problem *before* assuming the thing you just changed broke it — especially right after a Node/tool version was switched or uninstalled. Bonus: the newer Node version already satisfies the `vite@8` engine requirement that had separately blocked a dependency bump elsewhere in this file.

**Once actually run, `stop.mjs` claimed success while leaving the real backend/frontend/agent processes alive and serving traffic — the exact "wrapper PID vs. real worker PID" bug this repo has hit and fixed before (2026-08-22, `common/process-supervisor.ts`), reintroduced in the dev scripts that are supposed to prevent it.** `spawn('npm', ['run', 'dev'], { shell: true })` on Windows returns the PID of the `cmd.exe`/`npm` wrapper, not the actual `tsx watch`/vite worker underneath it. `taskkill /PID <wrapper> /T /F` is supposed to tree-kill the whole lineage, but if the wrapper has already exited on its own (confirmed live: `wmic` showed the recorded PID gone entirely) while its child is still running under a new PID, `/T` has no lineage left to walk — it reports success-looking failure ("process not found") and the real worker, the one actually holding the port, survives untouched. Caught only by directly curling the "stopped" backend and getting a real 200 back, not by trusting the script's own log output. **Rule now, generalizing the 2026-08-22 lesson**: a PID captured at spawn time is only as trustworthy as the process that's still alive to own it — for anything that can outlive an intermediate wrapper (any `shell: true` spawn on Windows, any watch-mode tool), prefer asking the OS for the process's current, independently-verifiable identity (who's listening on the port, matching by distinctive command line) over trusting a PID recorded once and never re-confirmed. `findProcessByPort()` is the fix here, mirroring the kill-by-name-then-verify pattern this same file's `stopEmulator()` already used successfully for the same reason (a shell's `$!`/PID doesn't reliably match what the OS needs to kill for a spawned GUI binary either).

## 2026-09-02

**`app.config = next` inside a Fastify plugin silently shadowed the config every other route reads.** The reload endpoint loaded fresh YAML, assigned it to `app.config`, and echoed the new values back — so it looked like it worked. It did not: Fastify gives each registered plugin an encapsulated instance that inherits decorators through the prototype chain, and a plain assignment defines an *own* property on that child scope. `builds` and `execution` would have kept reading the boot-time config forever. Two periodic sweeps had the same bug in a different shape — they closed over the `config` local in `server.ts` rather than reading `app.config` at tick time, so a changed retention policy would never have reached the build GC. **Rules now:** (1) a decorated value that is ever *reassigned* must be declared with `app.decorate(name, { getter, setter })`, not as a plain value — assignment then walks the prototype chain to one setter instead of shadowing; (2) when making something runtime-mutable that was previously fixed at boot, grep for every place the old value was *captured* (closures, intervals, module-level consts), not just every place it is read — every read site here was already fine, and every capture was wrong. Caught only because the route test asserted `app.config` had actually changed instead of trusting the response body, which is the general lesson: assert the state the rest of the system reads, not the value the handler just handed back to you.

**A "conservative" fallback that declines to infer can be less honest than one that infers.** Adding a `suiteKind` snapshot to runs raised the obvious question of what to do with the runs that predate it. Falling back to `null` felt like the careful answer — don't claim to know something that was never recorded. It was wrong, and a real aggregate showed it within minutes: one feature file rendered as two rows, an unqualified bucket holding all its history and a qualified one starting from zero, which is precisely the discontinuity the whole change existed to prevent. The kind was never actually unknown — it is a pure function of the suite string, computed by the same `classifySuite` the runner itself used to choose its flag at the time the run happened. **Rule now:** before treating a missing field as unknowable, check whether it is *derivable* from data you already have by the same rule that produced it originally. Recomputing a deterministic value is recovery, not guesswork; the two only look alike from a distance. And when introducing a field that participates in a grouping key, look at a real aggregate spanning the introduction — the discontinuity is invisible in unit tests, which have no "before".

**A port being held is not the same as a server being ready, and the hub opens that gap itself.** Appium orchestration adopts an already-listening server rather than replacing it, but "already listening" was decided solely by `GET /status`. The live-servers map is process memory, so `tsx watch` restarting the backend orphans a running Appium; a run starting while that orphan is still booting sees a silent `/status`, concludes the port is free, spawns its own, and dies on `EADDRINUSE`. It was confusing to diagnose because by the time it was investigated the orphan had exited and the port was genuinely free. **Rule now:** when adopting an existing process by probing its API, treat `EADDRINUSE` as a *third* state — not "free", not "ready", but "someone is there who has not opened their API yet" — and wait it out before failing. More generally, any registry of live child processes kept only in memory is invalidated by a restart, so the recovery path has to be able to re-adopt from the outside world rather than reading an empty map as "nothing is running".

## 2026-08-29 (requirement loss — "don't copy the implementation" quietly became "don't preserve the job")

**A rewrite that correctly refused the reference platform's bad mechanisms dropped several of its good jobs at the same time, and nobody noticed until a user asked why features had disappeared.** The pattern, repeated across four modules: the reference had a capability with a flawed implementation → the rewrite rightly rejected the *implementation* → nobody recorded a disposition for the *job* → the new module spec omitted or simplified it → the implementation faithfully followed the incomplete spec → the gap surfaced months later as "this existed before, why is it gone?". Concrete instances: per-viewer H264 was correctly refused, and tab-visibility pause, `sourceHost` routing and the lightweight JPEG path went with it; hardcoded post-install tap tours were correctly refused, and build provenance, changelog and uninstall went with them; ambiguous journey-by-time correlation was correctly refused, and failure-reason aggregation and test-case counts went with it. The tell was already visible in the tracker and read as good news: inventory counts, filter chips, multi-view, pipeline tabs and the build catalog were all logged as *recovered* — every one found by visual comparison **after** implementation, never by a requirements check before it. **Rule now:** when replacing a reference system, every source capability needs an explicit disposition — KEEP / REIMPLEMENT / ADAPT / DROP / BLOCKED — recorded before implementation, and "we didn't copy it" is not one of them. `docs/SOURCE_FEATURE_TRACEABILITY.md` now holds that matrix, and `SELF_REVIEW.md` requires updating it. The governing sentence: **preserve the job, replace the mechanism.**

**Self-review only compared code to spec — but a requirement can already be lost by the time the spec is written.** The drift check added earlier this same day ("diff the implementation against `docs/modules/*.md`") is a real improvement and would never have caught any of the above, because those capabilities are absent from the module specs too. ## 2026-08-29 (a repeated bug class finally got an abstraction)

**The same child-process bug kept reappearing in unrelated modules for a week before anyone treated it as one problem.** The list, all previously logged here as separate incidents: `spawn('npm')` failing with ENOENT on Windows; an `adb` child hanging because stdin was left open; killing a wrapper PID under `tsx watch` instead of the real worker; a process tree surviving cancellation; stale Node processes needing manual cleanup; Windows-vs-MSYS path translation. Each was diagnosed on its own, fixed locally, written up as its own lesson — and the next one arrived anyway. An external review was what named it as a class rather than a run of bad luck. **Rule now:** when the *same shape* of bug has been fixed in three or more places, stop fixing instances and build the one thing that owns it (here `common/process-supervisor.ts`: executable resolution, explicit stdio, tree-kill, timeouts, outcome normalization). The signal to watch for is writing a lesson entry that rhymes with an earlier one — that is the cue to abstract, and it fired several times before it was acted on. Note this deliberately did *not* become a seventh extracted package: consolidating a failure class inside the repo is a different, lower-risk act than publishing a generic library, and the package can come later if a second consumer ever proves it generic.

**A rejected promise and a nonzero exit are the same event to a user and completely different events to code — and that gap ate a stage.** `runCommand` resolved with an exit code but *rejected* on spawn failure. The nonzero-exit path updated the stage record and the run status; the rejection path unwound to an outer `catch` that only updated the run. So a Windows `npm` failure produced a run reading "Failed" with its "Install dependencies" stage stuck on "running" forever — visible to the user (screenshot) and confusing precisely because both halves were individually working as written. **Rule now:** when a function can finish in several ways, make every way the *same kind* of value — the supervisor returns a `RunOutcome` union and never rejects for a process-level failure, which makes "forgot to update the stage on this path" unrepresentable rather than merely discouraged. An error path that leaves state half-updated is worse than one that fails loudly, because it looks like a product bug rather than a crash.

**Two requirements were quietly contradictory and would have shipped as a data-loss bug.** The execution design asks for the run log to live in the workspace, for finished runs' logs to be readable, *and* for the workspace to be deleted when the run ends. All three had been written down as goals at different times; nobody put them side by side. Implementing "serve historical logs" first — the obvious order, since it was the user-visible complaint — would have produced a working endpoint that started returning 404s the moment workspace cleanup shipped. It was an external review that spotted the contradiction, not the code. **Rule now:** before implementing a persistence-adjacent feature, list every requirement touching the same directory and check they can all hold at once; if they cannot, fix the storage model first (here: split ephemeral `EXECUTIONS_DIR` from durable `EXECUTION_ARTIFACTS_DIR`). Contradictions between requirements written months apart are invisible to typecheck, tests, and code review alike — only an explicit inventory finds them.

**Counting every failure the same way let lab problems masquerade as application quality.** A run rejected because its device was already locked was stored as `status: 'failed'`, identical to a run whose test suite genuinely failed. Analytics then divided passes by *all* terminal runs, so contention in the lab — a scheduling artifact that never touched the app — pushed the reported pass rate down. With 100 real runs at 98% and 20 lock rejections, the dashboard would have said 81.7%. Nothing was broken in the usual sense; every individual piece did what it said. **Rule now:** keep "what happened to the orchestration" and "what the test said" as separate fields (`status` + `failureKind`), and make any rate metric state which population it divides by. A metric that silently mixes infrastructure noise into a quality number is worse than no metric, because it gets trusted. Corollary applied here: totals still count everything, so the lab problem stays *visible* — the fix was to stop miscounting it, not to hide it.

## 2026-08-29 (device streaming + guards — caught late, written up after the fact)

**A capability guard that queries a field nothing ever writes is a no-op that looks fully implemented.** `streaming.service.ts`'s iOS-simulator cap (`IOS_SIMULATOR_STREAM_CAP = 8`, guarding the documented `xcrun simctl` frame-drop limit) counted active sessions with `StreamSession.countDocuments({ ..., isSimulator: true })` — but `upsertSession()` never actually persisted `isSimulator` onto the document. A guard is untested until a test (or a real run) proves the value it reads is the value that was written, not a schema default.

Typecheck and lint were clean (every branch is reachable and well-typed; only the *order* was wrong). It was found twice independently and only because real coverage was finally added: once by an E2E spec that asserted the banner text, once by a component test. **Rule now:** when inserting a new condition into an existing precedence chain (ternary ladder, `switch`, guard sequence), explicitly re-derive the intended priority of *every* branch rather than appending at the front — and check whether a sibling element nearby encodes the same precedence independently, since two hand-maintained copies of one ordering is exactly where they diverge. ## 2026-08-28 (later)

## 2026-08-28

**The Android emulator's own Windows crash-reporter writes a full dump of the process environment into its startup log, and casually `tail`ing that log leaked a real secret into a chat transcript.** `scripts/start.sh` redirects `emulator.exe`'s stdout/stderr to `LOG_DIR/emulator.log` so boot progress can be inspected — routine, and needed for debugging a slow/failed boot. What wasn't obvious: emulator.exe's crashpad integration includes the *entire inherited environment* as crash-context annotations, written to that log on every launch, crash or not. A `tail` of that file while checking boot progress surfaced a real Hugging Face API token (`HUGGINGFACEHUB_API_TOKEN`) set as a machine-wide env var — unrelated to this project, just present in the shell's environment — which then got echoed straight into the conversation transcript. **Rule now:** treat any log produced by redirecting a spawned GUI/emulator process's raw stdout/stderr as potentially containing the full environment, not just that process's own intentional output — grep for the specific line needed (boot status, an error pattern) rather than `cat`/`head`/`tail`ing the whole file, especially before sharing it anywhere. `scripts/start.sh` now carries this warning inline above the emulator launch. When a secret does leak this way, the fix is rotation, not just not-repeating-it — a value already in a transcript or log file is compromised regardless of whether it gets displayed again.

**A `spawn()` call with no `stdio` option can hang indefinitely on Windows, and only surfaces as a long-lived child of a backgrounded watcher, not in a one-shot script.** The MJPEG/H264 capture sources spawned `adb` without an explicit `stdio` — Node defaults every stream to `'pipe'`, leaving `stdin` open and unconsumed. `adb exec-out screencap`/`screenrecord` never read stdin, but the open, never-closed pipe was enough to leave the process hung on some runs. A standalone verification script calling the exact same code succeeded cleanly; the same code running as a long-lived child of `tsx watch` in the real server hung. Diagnosed via `tasklist`/`wmic` showing the *same* `adb.exe` PID persisting across repeated checks (proof of a stuck, never-closing child), not via any error or log line — the process was simply silent forever. **Rule now:** any `spawn()` of a CLI that doesn't read stdin should pass `stdio: ['ignore', 'pipe', 'pipe']` explicitly — don't rely on the default. And when a spawned child "just hangs" with no error, check for a persisting PID across repeated `tasklist` samples before assuming the bug is upstream (device unresponsive, adb server stuck, etc.) — a one-shot repro script passing is not proof the same code is safe as a long-lived child of a different parent process.

**A `.env` value can be syntactically valid and still wrong for the process that reads it, if it was authored inside Git Bash without noticing the path convention doesn't survive into a `.env` file.** `ADB_PATH=/c/Users/Deepak/.../adb.exe` in `backend/.env` is a Git-Bash/MSYS-style path. It resolves correctly when Git Bash itself launches a process with that value passed inline as an env-var prefix (`ADB_PATH="/c/Users/..." npx tsx script.ts`) — Git Bash's own exec layer translates it. It does **not** resolve when a long-running Node server reads the literal string from a `.env` file and hands it straight to `child_process.spawn()`: native Windows `CreateProcess` has no idea what `/c/...` means, so every spawn failed with `ENOENT` (`code: -4058`). This silently tanked every live capture — no crash, no visible error in the UI (the capture source's own `error` → `teardown` → "next viewer starts fresh" path swallowed it into an infinite retry loop that looked like "starting" forever). Confirmed by temporarily instrumenting `tick()`'s `child.on('close', ...)` handler directly, which is what actually revealed the `-4058` code — reading the surrounding service/route code top-to-bottom found nothing wrong, because there wasn't anything wrong there. **Rule now:** any filesystem path env var meant for a Windows-native Node process must use a Windows-native form (`C:/...` or `C:\\...`), never the `/c/...` MSYS form, even though the MSYS form "just works" when typed directly into a Git Bash one-liner — that's Git Bash translating it for you, not evidence the value itself is portable.

**On Windows, killing a `tsx watch`-launched dev server by its wrapper PID doesn't kill its actual worker process, and repeating that mistake across a long session compounds into a real resource leak.** Across this session's many "restart the backend" cycles, each restart's kill step left the previous worker (and sometimes the `tsx watch` supervisor itself) alive — by session's end, **66 stale node processes** for this one project were still running, none of them the one actually serving traffic. This had been silently masking bugs too: a live-looking backend could in fact be an old, unfixed build still bound to the port, while a newer, fixed one sat orphaned never having bound anything. **Rule now:** on Windows, stop a `tsx watch`/`npm run dev` process tree with `taskkill //PID <pid> //T //F` (the `/T` tree-kill flag), not a bare `kill`/`taskkill //PID <pid> //F` on just the PID you happen to have — and periodically check `wmic process where "name='node.exe'" get ProcessId,CommandLine` for a project during a long session to catch drift before it reaches double digits.

## 2026-08-27

**`docker compose` had never actually been run, and the moment it was, three "verified" ESM-only package integrations turned out to be broken in the one environment that matters most: the real compiled production build.** `tsc`, compiling this backend to CommonJS, silently rewrites a literal `await import('some-esm-package')` into `require('some-esm-package')` wrapped in a resolved promise — confirmed by reading the compiled output directly. For an ESM-only dependency with no `require` export condition (`layered-config-ts`, `fastify-auth-kit`, `mongoose-index-guard` — every package this session bridged this way), that `require()` throws `ERR_PACKAGE_PATH_NOT_EXPORTED`. Every "verified" claim for these three integrations — including a full failure-reproduction cycle for `mongoose-index-guard` — was run under `tsx watch`, which uses its own loader and never downlevels the import. The actual production path (`npm run build && node dist/server.js`, exactly what the Dockerfiles run) was silently broken from the very first extraction (`layered-config-ts`, 2026-08-24) through this session, and nothing caught it because `docker compose up` was never once run in this whole build. **Rule now:** "works under `tsx watch`" and "works in production" are not the same claim for anything involving dynamic `import()` in a CommonJS-output TypeScript project — verify the compiled artifact (`node dist/...`, or better, the real container) whenever a fix specifically concerns module format/packaging, not just the dev loop. This is a sharper version of the 2026-08-26 lesson ("a package's own green tests verify the package, not the integration") — here even the *integration* passing wasn't enough, because the verification method itself didn't exercise the real runtime path.

Fixed with `backend/src/common/dynamic-import.ts`: a `new Function('specifier', 'return import(specifier)')` wrapper. `tsc` only rewrites `import()` expressions it can see syntactically in the AST; one hidden inside a string body passed to the `Function` constructor is invisible to that transform, so it survives as a genuine dynamic import at runtime. This is the standard, well-documented community workaround for this exact TypeScript/Node gap — not a novel hack.

That fix then broke the one existing test that exercised it for real (`config.service.test.ts`, 3 tests) with `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING` — Vitest runs test modules inside a `vm` sandbox that only wires up a dynamic-import callback for code its own transform pipeline handles, not for a separately-compiled `new Function` body. Fixed by mocking `common/dynamic-import` in that one test file to delegate to a plain `import()` written directly in the test file — Vitest's transform handles that correctly, and it's still a real import of the real package, not a stubbed fake, so the test still exercises actual `layered-config-ts` behavior end to end. **Rule reinforced:** a fix for one environment (plain Node) can break another (a test sandbox) in a way that looks unrelated at first (a VM/eval error, not an import error) — trace it to the actual mechanism rather than assuming it's a new, separate bug.

**Two Docker-specific bugs found by the same "actually run it" pass, unrelated to the module-format issue:** (1) both Dockerfiles ran `npm ci` from inside their own subdirectory, but this is an npm-workspaces monorepo whose lockfile lives at the repo root — `npm ci` failed immediately with `EUSAGE` on a completely fresh build, meaning the containers had never successfully built even once. Fixed by changing the build `context:` to the repo root and copying the root `package.json`/`package-lock.json` alongside each package's own, using `npm ci --workspace=<name>` to scope the install. (2) `STREAM_WS_PORT`/`VITE_STREAM_WS_URL` were wired through the env schema, both Dockerfiles, and docker-compose — a leftover from an earlier design where streaming had its own WebSocket port, before it was unified onto the same Fastify app/port as everything else (confirmed via `nginx.conf`, which already correctly proxies `/api/` including its WebSocket upgrade, and via a repo-wide grep finding zero real usages of either variable). **A Fastify hook that returns `void` instead of a Promise hangs every request it allows through.** The new agent-auth guard was written as `(req, reply): void`. ## 2026-08-25 (later)

**Registering a socket's `close` handler *after* an `await` loses the event, and leaked a viewer forever.** The stream route did `const { detach } = await streamingService.addViewer(...)` and only then `socket.on('close', detach)`. **Killing "the server" on Windows by its listening-port PID isn't reliable under `npm run dev` / `tsx watch`.** Tried to simulate a backend crash (to test `execution`'s orphan-recovery-on-restart path) by `taskkill`-ing the PID that `netstat` showed LISTENING on :3000. ## 2026-11-22 — Emulator crashes were the host GPU driver, not memory

**The emulator kept closing with "Android Emulator closed unexpectedly", and the first guess (low disk / low RAM) was only part of it.** With 43 GB disk and 7 GB RAM free it still crashed. The AVD ran `hw.gpu.mode = auto` on a hybrid Intel + NVIDIA laptop — the host-GPU renderer path is the classic crash source there — asked for 10 cores, and each crash left a stale `hardware-qemu.ini.lock` (a *directory*, so a plain `rm` fails) that made the next boot fail too. **Fix, now the default in `scripts/start.mjs`:** headless (`-no-window`, opt back in with `EMULATOR_WINDOW=1`), software GPU (`-gpu swiftshader_indirect`), cold boot (`-no-snapshot`), 2 cores / 2 GB; output discarded and an allowlisted environment passed so a crash dump cannot carry unrelated secrets; `stop.mjs` clears `*.lock` in the AVD dir once no emulator process is verified running. ## 2026-11-22 — Checks that passed for the wrong reason, and docs left behind

**`stop.mjs` killed the shell running it, twice.** Its process match ("command line mentions this repo, `tsx` and `src/server.ts`") also matched the Bash shell whose command line contained those words. **Rule now:** a kill-by-command-line match must also check the executable (`isRepoTsxNode`: the command must start with `node`), never only words that any shell invoking the script can contain.

**The accountability page and plan §9 fell a full batch behind the code.** `TODO.md` was updated with every commit, but `docs/accountability-2026-11.html`, `docs/reconciliation-plan-2026-11.md` §9 and `SOURCE_FEATURE_TRACEABILITY.md` were not, so eleven rows still said Gap for things that were fixed and pushed (CI, CSP, host-scoped presets, install warnings, branch-aware suites). ## 2026-11-22 — A check that cannot run must not report a verdict

**The Appium driver check said "no uiautomator2 driver installed" when the driver was installed.** A live run failed `appium_session` with that message; the next run, a minute later, passed the check, and `appium driver list --installed` listed the driver in about a second. `assertDriverInstalled` never looked at whether the listing command itself succeeded: a timeout, crash or spawn failure left the output empty, and empty output read as "driver missing". The same false message was seen on 2026-09-21 (TODO.md), when its cause (a Windows spawn error) was fixed but the reporting was not, so the next unrelated failure of the listing produced the same wrong advice. **Rule:** a probe whose command failed reports that it could not check, with the command's outcome; only a probe that ran may say what it found. Test: with `PATH` emptied the check now reports "Could not check", and fails against the old code.

## 2026-11-23 — A schema parse in a route must map to 400

**`POST /:id/rerun` answered a malformed body with a 500.** The rerun-failed change parsed its new body with `rerunBody.parse(...)`, which throws a raw `ZodError`; the central error handler only maps the typed `AppError`s, so the caller got "Something went wrong" instead of a 400 naming the bad field. Found a day later while live-checking the bulk routes, which copied the same call. The trigger route already did it right (`safeParse` then `ValidationError`); the new code did not follow it. **Rule:** route bodies go through `parseBody(schema, body)` in `execution.routes.ts` (a test pins the 400), and a live check of a new route includes one malformed body.

## 2026-11-23 — Mutation checks that passed, and a NUL byte from a heredoc

**Two deliberate breaks of the board's writer rules left every test green.** The resync test ended with a replay of the newer run, which hid the older replay's overwrite; the prep-failure test had no second run holding a node, so a release that ignored the run id looked the same. Both tests now assert the state right after the step that could go wrong, and include the other run. **Rule (already in SELF_REVIEW, applied again):** break the rule under test on purpose and watch a test fail before trusting it.

**An inline Python heredoc wrote a raw NUL byte into a source file**: `\u0000` inside the heredoc reached Python as an escape and was written as the byte itself (`grep` reported the file as binary). Caught by that grep and fixed the same minute. **Rule:** source edits go through script files written with the Write tool (as LESSONS already says); after any scripted edit, `grep -c` the edited line, and a "Binary file matches" means stop and look.
