# Mobile Hub — Lessons Learned

A running log of real mistakes made in this repo (bugs shipped, wrong assumptions, scope missed) and what changed as a result. Not a design-decision log — that's `docs/architecture-blueprint.md` and ADRs. Not a "things to watch out for in general" list — that's the "Lessons carried in from the reference architecture" section of root `CLAUDE.md`. This file is specific and retrospective: *we actually did X, here's what it cost, here's the rule now.*

Newest first. See root `CLAUDE.md` § Self-review for when to add an entry.

---

## 2026-08-25 (later)

**Registering a socket's `close` handler *after* an `await` loses the event, and leaked a viewer forever.** The stream route did `const { detach } = await streamingService.addViewer(...)` and only then `socket.on('close', detach)`. A socket that closed during that await — a fast navigate-away, a reload, React re-running an effect — fired `close` before any listener existed, so the viewer was never removed. The capture then had a phantom viewer, never reached idle teardown, and its process would have run forever. **Rule now:** when attaching a listener for an event that can fire during an in-flight `await`, register it *before* the await and reconcile afterwards (record the early close, then release immediately once the attach resolves). This generalises past sockets: any "set up resource, then register its cleanup" sequence with an await in the middle has the same hole.

**Two of the three bugs this session were found by the E2E suite, not by unit tests or by reading the code.** The viewer leak above surfaced as `viewerCount: 2` where 1 was expected; a WebSocket proxy gap surfaced as a banner that never said "Live". Both were invisible to typecheck, lint, and every unit test, because both lived in the seam between processes — browser to proxy to server. **Rule now:** treat the E2E suite as the place seam bugs get caught and keep investing there; when an E2E assertion disagrees with what the code "obviously" does, suspect the code first. Worth noting the failure mode too: the first instinct was "flaky test, make it poll" — polling was right for the eventually-consistent count, but it *stayed* wrong for 15s, which is what distinguished a real leak from a timing artifact. Give a suspected-flaky assertion enough time to prove itself before relaxing it.

**The API's own rate limit failed the test suite before the product did.** A full E2E run exceeded the hardcoded 200 requests/minute and produced a scatter of unrelated-looking 429s. The limit was also a latent production problem: it is global per IP, so many hosts heartbeating every 10 seconds plus several browsers polling share one budget, and behind a reverse proxy they may all appear as one IP. **Rule now:** operational limits belong in config, not in a literal — `RATE_LIMIT_MAX`/`RATE_LIMIT_WINDOW` are now env vars with the old value as the default. Same rule as the hardcoded `dbName`: if a value has to differ between dev, test, and production, it cannot be a constant in the source.

## 2026-08-25

**Three UI defects shipped clean through typecheck, lint, and build — and were only caught by rendering the page and looking at it.** (1) A device card passed the raw lock reason into its status badge, so `execution:6a8d088c4bccc7f2b1a6f35d` rendered inline and squeezed the device name down to `iPad ...` — an opaque id crowding out the one thing the card exists to show. (2) Analytics pass-rate bars reused the progress-bar treatment (accent fill, green when complete), so a 50% pass rate rendered accent-blue and read as "half loaded" rather than "half failing" — right pixels, wrong meaning. (3) Making the card clickable nested an `<a>` inside an `<a>`, which is invalid HTML and breaks click behavior; React warned about it in the browser console, where no static check would ever have seen it. **Rule now:** for UI work, "typecheck + lint + build pass" says nothing about whether the screen is correct — the same gap as the server-side `pino-pretty`/plugin-version entry from 2026-08-22. Render every route in a real browser with realistic data, screenshot it, *look at it*, and treat a clean console as part of the check. A ~30-line Playwright script does all of it and is worth writing before the design work, not after.

**Seeding realistic data was what made the defects visible at all.** With one emulator and a blank-ish database the layout looked fine; it was only after seeding two hosts, five real device names, three builds, and a mix of passed/failed/running runs that the truncation, the miscolored bar, and the empty-state gaps showed up. **Rule now:** verify UI against data that resembles production — varied name lengths, every status the system can emit, and at least one in-flight item — because the degenerate cases (one row, all-same-status, everything short) are exactly the ones that hide layout bugs.

## 2026-08-23

**`connectDB()` hardcoded `dbName: 'mobilehub'`, silently overriding whatever database `MONGODB_URI` named.** The E2E suite pointed a backend at `.../mobilehub_e2e` and carefully wiped that database before every run — including a safety guardrail refusing to wipe anything not named like a test DB — while the backend read and wrote `mobilehub` the entire time. So the isolation was theatre: the suite protected a database nobody was using and ran against the real dev data, which is precisely what the guardrail existed to prevent. It also directly violated root `CLAUDE.md`'s "**Not** hardcode host/port/paths — anything host-specific must be config." **Rule now:** a connection string is the single source of truth for what it addresses; never pass an option that can override part of it. More generally — this is the *same shape* as the `baseURL` bug below, found the same day: a configured value silently replaced by a hardcoded default in the same slot. When reviewing config plumbing, specifically ask "can anything downstream override this?", because both bugs were invisible until something pointed the config somewhere new.

**Dropping a MongoDB database out from under a running Mongoose process destroys its indexes, and Mongoose neither rebuilds them nor tells you.** Fixing the `dbName` bug above made the E2E suite's `dropDatabase()` actually hit the live database — which deleted the `users.email` unique index. mobile-hub maps Mongo's E11000 to a 409, so with no index duplicate registrations quietly returned **201**, and a real duplicate row got written. On the next restart Mongoose tried to rebuild the unique index, hit E11000 because of that duplicate, and **swallowed the error entirely** — no log, no crash, just an app running permanently without a uniqueness guarantee. Three separate bugs stacked into one confusing "expected 409, got 201". **Rules now:** (1) reset test databases by deleting documents, not dropping the database, so indexes survive; (2) treat a silently-missing index as a first-class failure mode — the E2E harness now asserts `users.email` exists and fails with an explanatory message instead of letting it surface as a nonsense assertion three tests later; (3) mobile-hub itself should surface Mongoose index-build failures rather than swallowing them (tracked in `docs/TODO.md`), because in production this same silence would mean duplicate accounts with no alert.

**A `baseURL` that worked in dev would have 404'd every request in Docker — and no check in the repo could have caught it.** `services/api.ts` set `baseURL: import.meta.env.VITE_API_URL ?? '/api'`, so the `/api` prefix was *replaced* rather than preserved whenever `VITE_API_URL` was set. Dev never sets it (Vite's proxy handles `/api`), so dev was fine — but `docker-compose.yml` passes `VITE_API_URL=http://localhost:3000` as a build arg, which would have produced a frontend calling `http://localhost:3000/devices` against a backend serving `/api/devices`. It typechecked, linted, and built cleanly, and sat undetected for as long as no feature code actually called the client. **Rule now:** when a config value has a fallback, check whether the fallback and the real value are the *same shape* — here one was a path prefix and the other an origin, silently swapped into the same slot. And treat "the deployment config sets this variable but local dev never does" as an untested code path by definition: if dev and prod resolve a value differently, at least one of them is unverified.

**The frontend pages rendered correctly in a real browser on the first try — because I checked instead of assuming.** After a subagent building the frontend pages died mid-task (hit a spend limit before reporting), it would have been easy to either assume its work was broken and redo it, or assume it was fine because `typecheck` passed. Neither would have been right: the work was complete and good, *and* it contained the `baseURL` bug above that no static check catches. Driving all 5 routes in headless Chromium against the live backend — asserting real data renders and the console is error-free — is what actually settled it. **Rule now:** "typecheck + lint + build pass" is not "it works" for a UI, in exactly the same way it wasn't for the server (see the 2026-08-22 pino-pretty/fastify-plugin entry). Playwright's browsers are already installed on this machine; a ~20-line script driving the real routes is a cheap, repeatable way to actually earn the "tested" checkbox.

## 2026-08-22

**Killing "the server" on Windows by its listening-port PID isn't reliable under `npm run dev` / `tsx watch`.** Tried to simulate a backend crash (to test `execution`'s orphan-recovery-on-restart path) by `taskkill`-ing the PID that `netstat` showed LISTENING on :3000. The server kept running — that PID belonged to a wrapper process in the `npm`/`tsx watch` chain, not the actual worker executing the code, and the in-flight execution run completed normally as if nothing happened. **Rule now:** to actually kill the worker, match the PID against the one in the process's own logs (pino's `(pid)` in every log line), not just whichever process owns the listening socket. Fell back to directly flipping state in MongoDB to simulate the orphan condition instead — a valid substitute when a real crash is awkward to induce, as long as the simulated state is exactly what the real failure would leave behind.

**Fastify plugin ambient-type-augmentation resolution is fragile enough to need a fallback, not just one fix.** Three separate times this session (`@fastify/jwt` inside `fastify-auth-kit`'s own build, the same package's `declare module` inside mobile-hub's `app.ts`, and `@fastify/websocket`'s `{ websocket: true }` route-overload in `execution.routes.ts`), a plugin's ambient `declare module` augmentation didn't apply where expected. A bare type-only anchor import (`import type {} from 'pkg'`) fixed the first two; it did *not* fix the third. **Rule now:** when a Fastify plugin's augmented types don't resolve, try the type-only anchor import first (cheap, usually works) — but if it doesn't, fall back to explicitly annotating the handler's parameters with the plugin's own exported types (e.g. `(socket: WebSocket, req: FastifyRequest) => ...` using `ws`'s own `WebSocket` type) rather than continuing to rely on overload inference. Don't assume the anchor trick generalizes to every case.

**`layered-config-ts`'s public API had three bugs that only surfaced when a real consumer (mobile-hub) used it — its own test suite, written by the same author in the same sitting, missed all three.** (1) `dist/` was gitignored with only `prepublishOnly` to build it — `prepublishOnly` only fires on `npm publish`, never on a `github:` install, so the consumer got a raw clone with no compiled output ("Cannot find module"). (2) `LoadLayeredConfigOptions<T extends Record<string, unknown>>` rejected any pre-typed named interface/const — only worked with inline object literals, which TS infers more leniently — but every real config type is a plain interface. (3) `schema: ZodType<Partial<T>>` used shallow `Partial`, but the package's actual behavior (and the documented use case) is a layer overriding one nested field without its siblings, which needs deep partial-ness — `Partial<T>` doesn't allow that shape at all. **Rule now:** a package's own test suite, written by its own author against its own mental model, is not evidence it works for a real consumer — it tends to reproduce the same blind spots the implementation has. Integrate a new package into its first real consumer *before* considering it done, not as a follow-up; that's where types-that-look-right-but-aren't actually get caught.

**`syncDevices` reset a locked device's status to `idle` on every routine re-sync.** The upsert unconditionally set `status: 'idle'` on every rediscovered device, including one currently locked (`in-use`). A host's periodic re-sync would silently overwrite the status while leaving the `lock` subdocument intact — an inconsistent state (shows idle, actually locked) that would have shipped invisibly since no test exercised "lock, then re-sync the same device." **Rule now:** sync only touches `status` for a brand-new device (schema default) or a reconnect (`offline → idle`); an already-known device's status is left alone. When writing an upsert-style sync/reconcile function, explicitly enumerate every status transition it's allowed to cause — don't let "upsert with a default" become "clobber on every call."

**A host going offline never released the devices it was holding locked.** `syncDevices` marked absent devices `offline` but never touched `lock`, so a device whose host dropped off the network stayed locked forever with no way out except a manual admin unlock. **Rule now:** any code path that marks a resource unreachable/offline must also release the derived state that assumed it was reachable (locks, active sessions, in-flight jobs) — offline and locked-by-someone are not independent facts here.

**`markStaleHostsOffline()` was written, fully correct, and never called.** It sat in `hosts.service.ts` as dead code — nothing wired it into a scheduler. Would have been invisible until a host actually went dark in front of a user and nothing happened. **Rule now:** a function that exists to run periodically is not "done" until something actually calls it on a schedule — grep for the call site as part of finishing the feature, not as a follow-up.

**JWTs were issued with no `expiresIn`.** `@fastify/jwt`'s `sign()` doesn't default to any expiry — a token signed without options lives forever. Easy to miss because everything *works* right up until it matters. **Rule now:** when wiring a new auth/token mechanism, expiry is part of the minimum viable implementation, not a hardening pass added later.

**Backend didn't actually boot.** Two separate issues, both invisible to `tsc --noEmit` and `eslint`: (1) `pino-pretty` was referenced by name as a log transport in `app.ts` but never added to `package.json` — crashed on first `npm run dev`. (2) `fastify` was pinned to `^5.0.0` while every `@fastify/*` plugin was pinned to majors built for Fastify v4 — crashed on plugin registration with a version-mismatch error. **Rule now:** typecheck and lint passing is not evidence the server starts. "Built" and "tested" are different checklist states in `TODO.md` for exactly this reason — always confirm "tested" by actually booting it, not by inferring it from a clean typecheck.

**`device.model.ts` declared a field literally named `model`.** Collided with Mongoose `Document`'s own `model()` method, breaking `tsc --noEmit` the moment strict checking touched that interface. Fixed via `Omit<Document, 'model'>`. **Rule now:** when a domain field name is also a method/property on a base class you're extending (Mongoose `Document`, but this generalizes), check for the collision before it surfaces as a confusing structural-typing error three files away.
