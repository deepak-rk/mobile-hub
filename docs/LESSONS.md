# Mobile Hub — Lessons Learned

A running log of real mistakes made in this repo (bugs shipped, wrong assumptions, scope missed) and what changed as a result. Not a design-decision log — that's `docs/architecture-blueprint.md` and ADRs. Not a "things to watch out for in general" list — that's the "Lessons carried in from the reference architecture" section of root `CLAUDE.md`. This file is specific and retrospective: *we actually did X, here's what it cost, here's the rule now.*

Newest first. See root `CLAUDE.md` § Self-review for when to add an entry.

---

## 2026-08-27 (yet later still)

**A new operational rate limit needs the same "raise it for the E2E suite" treatment as the first one did, and this was nearly missed again.** Landing an independent, tighter `AUTH_RATE_LIMIT_MAX` (20/min) broke `auth.spec.ts` at its real default — confirmed by actually running the suite without an override before assuming it was fine, not by reasoning about call counts. The exact same class of gap as the original global `RATE_LIMIT_MAX` (2026-08-26): any new per-route limit is another value the E2E suite's env needs raised, in both the README and CI, or the suite silently starts failing against its own recommended run instructions. **Rule now:** whenever a new rate limit (or similar per-request cap) is added anywhere in the backend, check the E2E suite against it for real before considering the backend change done — this is now the second time, so treat it as a standing checklist item, not a one-off catch.

**Also: verify a fix by testing it at its real default, not just with your test override left in place.** The 5-attempts-then-429 live proof for the rate limiter itself used a deliberately lowered `AUTH_RATE_LIMIT_MAX=5` to keep the test fast — correct for proving the limiter works. But the E2E-suite question ("does this break existing callers?") needed the opposite: running at the real, unmodified default, not a convenient override. Conflating "I tested this feature" with "I tested this feature's default configuration against everything that depends on it" is an easy mistake in the same pass.

## 2026-08-27 (yet later)

**An outside review of `docs/TODO.md` found real drift this repo's own update discipline had missed: a stale "24 API tests, UI pending" line untouched since 2026-08-23, and two module sections still claiming "zero `.test.ts`" after both gained real coverage.** The rule "update the tracker in the same session as the work" had been followed for the *new* facts each session added, but nobody had swept for older lines the new facts silently made false elsewhere in the same file. **Rule now:** when adding a "N tests" or "zero tests" claim, grep the file for the same claim shape once in a while, not just add the new true line next to old ones that quietly became false.

**The same review caught a real inconsistency in this repo's own stub convention: `pulling`/`restoring_cache` silently reported `'skipped'`, the same status legitimately used for `installing` when a caller simply chose not to supply a step — but one means "not needed" and the other means "doesn't exist yet," and collapsing them let a caller believe a repo was pulled when nothing happened.** The `builds` module already had the right shape for this exact situation (the Nexus/S3/webhook providers reject with a clear message); `execution` just hadn't applied it. **Rule now:** when a codebase already has a correct pattern for "this isn't built yet," a new stub that quietly does the same thing differently is worth noticing and reconciling, not just replicating from whatever felt natural for that specific stage — inconsistent stub shapes are the corner logging/reviews will not think to check twice.

## 2026-08-27 (later still)

**A stubbed feature's own doc comment turned out to be wrong about the underlying platform, not just incomplete about the implementation.** `docs/TODO.md` said H264 "slots in without redesign" since the protocol was already part of the session key — true for that layer, but investigating the actual capture path found `adb screenrecord` on this environment's emulator has no `--output-format` flag and cannot write to stdout at all, contradicting what the existing code comments implied about a pipeable raw stream. **Rule now:** when picking up a stub, verify the platform assumption behind it before building on top of it, especially when the existing note was written without ever having tried the actual command — a plausible-sounding assumption about a device API is still a guess until it's run for real.

**Proving a failure is not your code's fault is worth the extra step, and is different work from proving your code is correct.** H264 browser playback didn't work; the natural next move would have been to keep debugging the WS relay / blob-swap pipeline. Instead, a captured segment was pulled directly via `adb` (bypassing the app's pipeline entirely) and served to Chrome's own `<video>` element from a plain local HTTP server — still stuck at `readyState 0` with no error, at two different bitrate/resolution settings. That's what actually justifies "this is an emulator encoder problem, not my code" rather than merely suspecting it. **Rule now:** when a failure could plausibly be either "my integration" or "the thing I'm integrating with," construct the minimal reproduction that isolates which one — don't stop at "I checked my code and it looks right."

**An honest "this doesn't fully work yet" is more valuable than a plausible-looking "done."** The H264 work shipped anyway — the capture/relay architecture is real, tested, and useful on its own even with playback unverified — but the UI toggle's label was corrected from "H264 (smoother, ~2s behind)" (implies it works) to "H264 (experimental)" with an honest tooltip, and every doc/commit describing it says exactly what's proven versus what isn't. **Rule now:** a feature that is partially built and honestly labeled as such is worth merging; a feature that overclaims what it does is worse than not shipping it at all, because the overclaim is what someone else trusts later.

## 2026-08-27 (later)

**A new device filter bar broke an existing E2E test in a way that revealed the test had been fragile all along, not just outdated.** `devices.spec.ts` asserted `page.getByText('Idle', { exact: true })` against the whole page. The new filter's `<option value="idle">Idle</option>` gave the page a second "Idle" text node, which Playwright resolves as present-but-hidden (inside a closed `<select>`) — and `.first()` picked it up instead of the real status badge, failing with "expected visible, received hidden." The fix wasn't just re-scoping to the new element: the *original* locator, built from `page.locator('a', { hasText: device.name })`, matched only the small device-name `<Link>` — the status badge is a sibling element, never actually nested inside that `<a>` at all. The assertion had been passing only because an unscoped `getByText` happened to find the right text somewhere on the page, not because the locator actually proved what the test claimed. **Rule now:** when new UI breaks an existing test, check whether the old locator was ever really scoped to what the test says it's asserting, before assuming the fix is just "update the selector for the new element." Prefer a stable structural anchor (here, `react-design-kit`'s `.rdk-card` class) over an incidental one (an `<a>` that happened to contain the right text by coincidence of layout, not by relationship).

## 2026-08-27

**`docker compose` had never actually been run, and the moment it was, three "verified" ESM-only package integrations turned out to be broken in the one environment that matters most: the real compiled production build.** `tsc`, compiling this backend to CommonJS, silently rewrites a literal `await import('some-esm-package')` into `require('some-esm-package')` wrapped in a resolved promise — confirmed by reading the compiled output directly. For an ESM-only dependency with no `require` export condition (`layered-config-ts`, `fastify-auth-kit`, `mongoose-index-guard` — every package this session bridged this way), that `require()` throws `ERR_PACKAGE_PATH_NOT_EXPORTED`. Every "verified" claim for these three integrations — including a full failure-reproduction cycle for `mongoose-index-guard` — was run under `tsx watch`, which uses its own loader and never downlevels the import. The actual production path (`npm run build && node dist/server.js`, exactly what the Dockerfiles run) was silently broken from the very first extraction (`layered-config-ts`, 2026-08-24) through this session, and nothing caught it because `docker compose up` was never once run in this whole build. **Rule now:** "works under `tsx watch`" and "works in production" are not the same claim for anything involving dynamic `import()` in a CommonJS-output TypeScript project — verify the compiled artifact (`node dist/...`, or better, the real container) whenever a fix specifically concerns module format/packaging, not just the dev loop. This is a sharper version of the 2026-08-26 lesson ("a package's own green tests verify the package, not the integration") — here even the *integration* passing wasn't enough, because the verification method itself didn't exercise the real runtime path.

Fixed with `backend/src/common/dynamic-import.ts`: a `new Function('specifier', 'return import(specifier)')` wrapper. `tsc` only rewrites `import()` expressions it can see syntactically in the AST; one hidden inside a string body passed to the `Function` constructor is invisible to that transform, so it survives as a genuine dynamic import at runtime. This is the standard, well-documented community workaround for this exact TypeScript/Node gap — not a novel hack.

That fix then broke the one existing test that exercised it for real (`config.service.test.ts`, 3 tests) with `ERR_VM_DYNAMIC_IMPORT_CALLBACK_MISSING` — Vitest runs test modules inside a `vm` sandbox that only wires up a dynamic-import callback for code its own transform pipeline handles, not for a separately-compiled `new Function` body. Fixed by mocking `common/dynamic-import` in that one test file to delegate to a plain `import()` written directly in the test file — Vitest's transform handles that correctly, and it's still a real import of the real package, not a stubbed fake, so the test still exercises actual `layered-config-ts` behavior end to end. **Rule reinforced:** a fix for one environment (plain Node) can break another (a test sandbox) in a way that looks unrelated at first (a VM/eval error, not an import error) — trace it to the actual mechanism rather than assuming it's a new, separate bug.

**Two Docker-specific bugs found by the same "actually run it" pass, unrelated to the module-format issue:** (1) both Dockerfiles ran `npm ci` from inside their own subdirectory, but this is an npm-workspaces monorepo whose lockfile lives at the repo root — `npm ci` failed immediately with `EUSAGE` on a completely fresh build, meaning the containers had never successfully built even once. Fixed by changing the build `context:` to the repo root and copying the root `package.json`/`package-lock.json` alongside each package's own, using `npm ci --workspace=<name>` to scope the install. (2) `STREAM_WS_PORT`/`VITE_STREAM_WS_URL` were wired through the env schema, both Dockerfiles, and docker-compose — a leftover from an earlier design where streaming had its own WebSocket port, before it was unified onto the same Fastify app/port as everything else (confirmed via `nginx.conf`, which already correctly proxies `/api/` including its WebSocket upgrade, and via a repo-wide grep finding zero real usages of either variable). Removed entirely rather than left as dead config. Also added a `BUILDS_DIR` volume to docker-compose — it had one for `EXECUTIONS_DIR` but not its sibling, so container build artifacts would have been silently ephemeral, gone on every container recreate.

## 2026-08-26

**"`npm test` needs no database" was true by accident, not by design, and two new test files broke it.** `config/env.ts` calls `process.exit(1)` at module load if `MONGODB_URI`/`JWT_SECRET` are missing — correct for the server, since a misconfigured deployment should refuse to boot. But no `vitest.config.ts` existed to set safe dummy values for tests, so the promise in backend/CLAUDE.md ("no database required") only held because, by coincidence, no existing test file imported anything that transitively pulled in `env.ts`. The new `builds.service.test.ts` and `execution.service.test.ts` (this session's test-coverage round) import their service files directly, which read `BUILDS_DIR`/`EXECUTIONS_DIR` off `env` — neither test touches Mongo or reads those env-derived paths for real, but the module-load-time `process.exit(1)` doesn't care, and it silently killed the whole vitest worker for those two files with `npm test` run bare (no env vars set), exactly how CI or a fresh clone would run it. Fixed with a `vitest.config.ts` setting dummy `MONGODB_URI`/`JWT_SECRET` for the test environment only — no test ever connects with them. **Rule now:** a "no database required" claim about a test suite needs a real from-scratch verification (`env -u MONGODB_URI -u JWT_SECRET npm test`, not just `npm test` in a shell that happens to have them exported already) — and a module that fails fast at *import time* rather than at first use is a landmine for any future test file that imports it only incidentally.

**The same "GitHub repo created but never pushed" gotcha hit three times in one session, on three different packages** (`ts-format-utils`, `react-design-kit`, `use-resilient-websocket` — every extracted package this session except the first one integrated). All were created as empty GitHub repos before this session's work started, and every `github:` install attempt failed with a git-checkout error that looks like a packaging problem but isn't. `git ls-remote <url> HEAD` returning nothing is the actual signal, written down after the first occurrence and still cheap to check on the second and third — checked immediately each time after that, so the cost per repeat dropped to seconds. **Rule reinforced:** run `git ls-remote` as the *first* check on any `github:` install failure, not a fallback after other theories are exhausted — and expect this specifically whenever a batch of sibling repos was created together, since "created" and "pushed" turned out not to be the same event across this whole batch.

**A "generic, verified, ready to publish" extracted package still broke on first real integration.** `mongoose-index-guard` (extracted from this repo's `ensure-indexes.ts`) had 17 passing tests, clean typecheck/lint/build, and a proven live boot cycle in its own repo before mobile-hub ever consumed it. Wiring it into `server.ts` with a plain `import` failed immediately with `ERR_PACKAGE_PATH_NOT_EXPORTED` — the package is ESM-only and this backend is CommonJS, and its own test suite could never have caught that because it never runs from inside a CommonJS project. The fix (dynamic `await import()`) is the exact pattern already established for `layered-config-ts` and `fastify-auth-kit`, so this is now the third dependency bridged this way. **Rule now:** a package's own green tests verify the package; they do not verify integration. Before trusting an extracted package as "done," wire it into the real consumer with the real install method (`file:` first is fine, but confirm with the actual `github:` install before calling it finished) and run the app, not just the package's suite — this is the same lesson as the `layered-config-ts` API bugs from 2026-08-24, applied one level earlier in the pipeline (this time the break was in packaging/module format, not the API surface itself).

**Re-verifying a bug fix means reproducing the original failure again, not just checking the happy path.** After swapping in the package, "the server boots" was not enough evidence that the fix still worked — the entire point of `ensureIndexes` is what it does when indexes are broken, not when they're fine. Re-ran the original repro (drop `users.email`'s unique index, insert two duplicate emails directly, restart) against the real published package and confirmed the server still refuses to boot with the exact E11000 detail, then confirmed a clean restart after fixing the duplicates. A green health check on a fresh database would have missed a regression in the one behavior that matters.

**A `github:` install can fail for a reason that has nothing to do with the package.** Swapping `ts-format-utils` from a local `file:` path to `github:deepak-rk/ts-format-utils` failed with `npm ERR! The git reference could not be found` / `checkout null` — not a bug in the package, but because the repo had been created on GitHub and never actually pushed to (`git ls-remote` returned nothing). Easy to misdiagnose as a packaging problem and go looking in the wrong place. **Rule now:** when a `github:` install fails, check `git ls-remote <url> HEAD` before assuming the package is broken — an empty result means "never pushed," not "broken."

**Consuming an extracted formatting utility surfaced one deliberate behavior change, not a bug: `formatRelative`'s ladder now extends to week/month/year, where the original capped at "N days ago" forever.** This is a real difference a consumer must decide about, not something to silently inherit. Checked whether any test — unit or E2E — asserted exact relative-time wording (none did) before accepting it as a UX improvement. **Rule now:** when generalizing a package changes an existing default's *output*, not just its *options*, that is a decision for the integrating change to make and record deliberately — check what actually depends on the old behavior rather than assuming either "nothing does" or "everything does."

**A Fastify hook that returns `void` instead of a Promise hangs every request it allows through.** The new agent-auth guard was written as `(req, reply): void`. Fastify picks how to run a hook from its arity: with two parameters it expects a Promise back, so a plain `void` return means it never resolves and `done()` is never called. The result was perfectly inverted from what a bug usually looks like — *rejections* worked (sending a reply ends the request on its own) while every *authorised* request hung forever. Unit tests passed too, because calling the function directly and asserting on the reply never exercises Fastify's hook runner. Only curling the real server showed it, as three requests that logged "incoming" and never logged "completed". **Rule now:** Fastify hooks and preHandlers are `async` unless they take the third `done` argument, and a guard is not verified until a request that *passes* it has been observed completing — testing only the rejection path leaves the more common path untested.


**A host going offline left its devices reading as available.** `markStaleHostsOffline` flipped the *host* to offline when its agent stopped heartbeating, but nothing touched that host's devices — so they sat at `idle`, and the UI offered them for locking and for running tests against a machine that wasn't there. The bug was invisible until an actual agent was run and then killed; every existing test covered the mirror case (a host that *keeps* reporting but drops one device) and none covered the host itself disappearing. **Rule now:** when a parent resource becomes unreachable, reconcile everything that was only reachable *through* it — the same release-the-derived-state rule already learned for device locks, applied one level up. And when a rule like that is written down, check whether it holds at every level of the hierarchy, not just the level where it was first noticed.

**Building the agent is what surfaced it.** Nothing about the API contract or the existing tests hinted at the gap; it took standing up the real host-side loop, watching it register devices, then killing it and looking at what the API still claimed. **Rule now:** a component that only ever exists as "something POSTs to this endpoint" is under-tested by construction — the missing piece is usually where the interesting failure modes live. Build the real client before assuming the server contract is complete.

## 2026-08-25 (later)

**Registering a socket's `close` handler *after* an `await` loses the event, and leaked a viewer forever.** The stream route did `const { detach } = await streamingService.addViewer(...)` and only then `socket.on('close', detach)`. A socket that closed during that await — a fast navigate-away, a reload, React re-running an effect — fired `close` before any listener existed, so the viewer was never removed. The capture then had a phantom viewer, never reached idle teardown, and its process would have run forever. **Rule now:** when attaching a listener for an event that can fire during an in-flight `await`, register it *before* the await and reconcile afterwards (record the early close, then release immediately once the attach resolves). This generalises past sockets: any "set up resource, then register its cleanup" sequence with an await in the middle has the same hole.

**Two of the three bugs this session were found by the E2E suite, not by unit tests or by reading the code.** The viewer leak above surfaced as `viewerCount: 2` where 1 was expected; a WebSocket proxy gap surfaced as a banner that never said "Live". Both were invisible to typecheck, lint, and every unit test, because both lived in the seam between processes — browser to proxy to server. **Rule now:** treat the E2E suite as the place seam bugs get caught and keep investing there; when an E2E assertion disagrees with what the code "obviously" does, suspect the code first. Worth noting the failure mode too: the first instinct was "flaky test, make it poll" — polling was right for the eventually-consistent count, but it *stayed* wrong for 15s, which is what distinguished a real leak from a timing artifact. Give a suspected-flaky assertion enough time to prove itself before relaxing it.

**The API's own rate limit failed the test suite before the product did.** A full E2E run exceeded the hardcoded 200 requests/minute and produced a scatter of unrelated-looking 429s. The limit was also a latent production problem: it is global per IP, so many hosts heartbeating every 10 seconds plus several browsers polling share one budget, and behind a reverse proxy they may all appear as one IP. **Rule now:** operational limits belong in config, not in a literal — `RATE_LIMIT_MAX`/`RATE_LIMIT_WINDOW` are now env vars with the old value as the default. Same rule as the hardcoded `dbName`: if a value has to differ between dev, test, and production, it cannot be a constant in the source.

## 2026-08-25

**Three UI defects shipped clean through typecheck, lint, and build — and were only caught by rendering the page and looking at it.** (1) A device card passed the raw lock reason into its status badge, so `execution:6a8d088c4bccc7f2b1a6f35d` rendered inline and squeezed the device name down to `iPad ...` — an opaque id crowding out the one thing the card exists to show. (2) Analytics pass-rate bars reused the progress-bar treatment (accent fill, green when complete), so a 50% pass rate rendered accent-blue and read as "half loaded" rather than "half failing" — right pixels, wrong meaning. (3) Making the card clickable nested an `<a>` inside an `<a>`, which is invalid HTML and breaks click behavior; React warned about it in the browser console, where no static check would ever have seen it. **Rule now:** for UI work, "typecheck + lint + build pass" says nothing about whether the screen is correct — the same gap as the server-side `pino-pretty`/plugin-version entry from 2026-08-22. Render every route in a real browser with realistic data, screenshot it, *look at it*, and treat a clean console as part of the check. A ~30-line Playwright script does all of it and is worth writing before the design work, not after.

**Seeding realistic data was what made the defects visible at all.** With one emulator and a blank-ish database the layout looked fine; it was only after seeding two hosts, five real device names, three builds, and a mix of passed/failed/running runs that the truncation, the miscolored bar, and the empty-state gaps showed up. **Rule now:** verify UI against data that resembles production — varied name lengths, every status the system can emit, and at least one in-flight item — because the degenerate cases (one row, all-same-status, everything short) are exactly the ones that hide layout bugs.

## 2026-08-23

**`connectDB()` hardcoded `dbName: 'mobilehub'`, silently overriding whatever database `MONGODB_URI` named.** The E2E suite pointed a backend at `.../mobilehub_e2e` and carefully wiped that database before every run — including a safety guardrail refusing to wipe anything not named like a test DB — while the backend read and wrote `mobilehub` the entire time. So the isolation was theatre: the suite protected a database nobody was using and ran against the real dev data, which is precisely what the guardrail existed to prevent. It also directly violated root `CLAUDE.md`'s "**Not** hardcode host/port/paths — anything host-specific must be config." **Rule now:** a connection string is the single source of truth for what it addresses; never pass an option that can override part of it. More generally — this is the *same shape* as the `baseURL` bug below, found the same day: a configured value silently replaced by a hardcoded default in the same slot. When reviewing config plumbing, specifically ask "can anything downstream override this?", because both bugs were invisible until something pointed the config somewhere new.

**Dropping a MongoDB database out from under a running Mongoose process destroys its indexes, and Mongoose neither rebuilds them nor tells you.** Fixing the `dbName` bug above made the E2E suite's `dropDatabase()` actually hit the live database — which deleted the `users.email` unique index. mobile-hub maps Mongo's E11000 to a 409, so with no index duplicate registrations quietly returned **201**, and a real duplicate row got written. On the next restart Mongoose tried to rebuild the unique index, hit E11000 because of that duplicate, and **swallowed the error entirely** — no log, no crash, just an app running permanently without a uniqueness guarantee. Three separate bugs stacked into one confusing "expected 409, got 201". **Rules now:** (1) reset test databases by deleting documents, not dropping the database, so indexes survive; (2) treat a silently-missing index as a first-class failure mode — the E2E harness now asserts `users.email` exists and fails with an explanatory message instead of letting it surface as a nonsense assertion three tests later; (3) mobile-hub itself should surface Mongoose index-build failures rather than swallowing them (tracked in `docs/TODO.md`), because in production this same silence would mean duplicate accounts with no alert.

**A `baseURL` that worked in dev would have 404'd every request in Docker — and no check in the repo could have caught it.** `services/api.ts` set `baseURL: import.meta.env.VITE_API_URL ?? '/api'`, so the `/api` prefix was *replaced* rather than preserved whenever `VITE_API_URL` was set. Dev never sets it (Vite's proxy handles `/api`), so dev was fine — but `docker-compose.yml` passes `VITE_API_URL=http://localhost:3000` as a build arg, which would have produced a frontend calling `http://localhost:3000/devices` against a backend serving `/api/devices`. It typechecked, linted, and built cleanly, and sat undetected for as long as no feature code actually called the client. **Rule now:** when a config value has a fallback, check whether the fallback and the real value are the *same shape* — here one was a path prefix and the other an origin, silently swapped into the same slot. And treat "the deployment config sets this variable but local dev never does" as an untested code path by definition: if dev and prod resolve a value differently, at least one of them is unverified.

**The frontend pages rendered correctly in a real browser on the first try — because I checked instead of assuming.** After a subagent building the frontend pages died mid-task (hit a spend limit before reporting), it would have been easy to either assume its work was broken and redo it, or assume it was fine because `typecheck` passed. Neither would have been right: the work was complete and good, *and* it contained the `baseURL` bug above that no static check catches. Driving all 5 routes in headless Chromium against the live backend — asserting real data renders and the console is error-free — is what actually settled it. **Rule now:** "typecheck + lint + build pass" is not "it works" for a UI, in exactly the same way it wasn't for the server (see the 2026-08-22 pino-pretty/fastify-plugin entry). Playwright's browsers are already installed on this machine; a ~20-line script driving the real routes is a cheap, repeatable way to actually earn the "tested" checkbox.

## 2026-08-22

**Killing "the server" on Windows by its listening-port PID isn't reliable under `npm run dev` / `tsx watch`.** Tried to simulate a backend crash (to test `execution`'s orphan-recovery-on-restart path) by `taskkill`-ing the PID that `netstat` showed LISTENING on :3000. The server kept running — that PID belonged to a wrapper process in the `npm`/`tsx watch` chain, not the actual worker executing the code, and the in-flight execution run completed normally as if nothing happened. **Rule now:** to actually kill the worker, match the PID against the one in the process's own logs (pino's `(pid)` in every log line), not just whichever process owns the listening socket. Fell back to directly flipping state in MongoDB to simulate the orphan condition instead — a valid substitute when a real crash is awkward to induce, as long as the simulated state is exactly what the real failure would leave behind.

**Fastify plugin ambient-type-augmentation resolution is fragile enough to need a fallback, not just one fix.** Three separate times this session (`@fastify/jwt` inside `fastify-auth-kit`'s own build, the same package's `declare module` inside mobile-hub's `app.ts`, and `@fastify/websocket`'s `{ websocket: true }` route-overload in `execution.routes.ts`), a plugin's ambient `declare module` augmentation didn't apply where expected. A bare type-only anchor import (`import type {} from 'pkg'`) fixed the first two; it did *not* fix the third. **Rule now:** when a Fastify plugin's augmented types don't resolve, try the type-only anchor import first (cheap, usually works) — but if it doesn't, fall back to explicitly annotating the handler's parameters with the plugin's own exported types (e.g. `(socket: WebSocket, req: FastifyRequest) => ...` using `ws`'s own `WebSocket` type) rather than continuing to rely on overload inference. Don't assume the anchor trick generalizes to every case.

**`layered-config-ts`'s public API had three bugs that only surfaced when a real consumer (mobile-hub) used it — its own test suite, written by the same author in the same sitting, missed all three.** (1) `dist/` was gitignored with only `prepublishOnly` to build it — `prepublishOnly` only fires on `npm publish`, never on a `github:` install, so the consumer got a raw clone with no compiled output ("Cannot find module"). (2) `LoadLayeredConfigOptions<T extends Record<string, unknown>>` rejected any pre-typed named interface/const — only worked with inline object literals, which TS infers more leniently — but every real config type is a plain interface. (3) `schema: ZodType<Partial<T>>` used shallow `Partial`, but the package's actual behavior (and the documented use case) is a layer overriding one nested field without its siblings, which needs deep partial-ness — `Partial<T>` doesn't allow that shape at all. **Rule now:** a package's own test suite, written by its own author against its own mental model, is not evidence it works for a real consumer — it tends to reproduce the same blind spots the implementation has. Integrate a new package into its first real consumer *before* considering it done, not as a follow-up; that's where types-that-look-right-but-aren't actually get caught.

**`syncDevices` reset a locked device's status to `idle` on every routine re-sync.** The upsert unconditionally set `status: 'idle'` on every rediscovered device, including one currently locked (`in-use`). A host's periodic re-sync would silently overwrite the status while leaving the `lock` subdocument intact — an inconsistent state (shows idle, actually locked) that would have shipped invisibly since no test exercised "lock, then re-sync the same device." **Rule now:** sync only touches `status` for a brand-new device (schema default) or a reconnect (`offline → idle`); an already-known device's status is left alone. When writing an upsert-style sync/reconcile function, explicitly enumerate every status transition it's allowed to cause — don't let "upsert with a default" become "clobber on every call."

**A host going offline never released the devices it was holding locked.** `syncDevices` marked absent devices `offline` but never touched `lock`, so a device whose host dropped off the network stayed locked forever with no way out except a manual admin unlock. **Rule now:** any code path that marks a resource unreachable/offline must also release the derived state that assumed it was reachable (locks, active sessions, in-flight jobs) — offline and locked-by-someone are not independent facts here.

**`markStaleHostsOffline()` was written, fully correct, and never called.** It sat in `hosts.service.ts` as dead code — nothing wired it into a scheduler. Would have been invisible until a host actually went dark in front of a user and nothing happened. **Rule now:** a function that exists to run periodically is not "done" until something actually calls it on a schedule — grep for the call site as part of finishing the feature, not as a follow-up.

**JWTs were issued with no `expiresIn`.** `@fastify/jwt`'s `sign()` doesn't default to any expiry — a token signed without options lives forever. Easy to miss because everything *works* right up until it matters. **Rule now:** when wiring a new auth/token mechanism, expiry is part of the minimum viable implementation, not a hardening pass added later.

**Backend didn't actually boot.** Two separate issues, both invisible to `tsc --noEmit` and `eslint`: (1) `pino-pretty` was referenced by name as a log transport in `app.ts` but never added to `package.json` — crashed on first `npm run dev`. (2) `fastify` was pinned to `^5.0.0` while every `@fastify/*` plugin was pinned to majors built for Fastify v4 — crashed on plugin registration with a version-mismatch error. **Rule now:** typecheck and lint passing is not evidence the server starts. "Built" and "tested" are different checklist states in `TODO.md` for exactly this reason — always confirm "tested" by actually booting it, not by inferring it from a clean typecheck.

**`device.model.ts` declared a field literally named `model`.** Collided with Mongoose `Document`'s own `model()` method, breaking `tsc --noEmit` the moment strict checking touched that interface. Fixed via `Omit<Document, 'model'>`. **Rule now:** when a domain field name is also a method/property on a base class you're extending (Mongoose `Document`, but this generalizes), check for the collision before it surfaces as a confusing structural-typing error three files away.
