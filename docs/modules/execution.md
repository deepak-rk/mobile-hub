## Purpose

Orchestrate end-to-end mobile test runs: clone the automation repo, restore cached dependencies, install fresh ones when needed, invoke the test runner against a locked device, stream logs to the frontend in real time, and store results. The platform adapts to each organisation's repo structure and test framework via config — it does not assume a fixed layout.

---

## The core problems this module solves

1. **Framework fragmentation.** Teams use WebdriverIO, raw Appium clients, Espresso, XCUITest, and others. No single execution model works for all. Mobile Hub's `automation` config block lets each org/project declare its own runner and directory structure.

2. **Dependency install overhead.** `npm install` on every run is slow and unnecessary when `package.json` hasn't changed. A cache layer with a correct, collision-resistant key eliminates redundant installs.

3. **Opaque run state.** Most OSS tools give you a log file after the run ends. Mobile Hub pushes stage transitions and log lines in real time via WebSocket (stages) and SSE (log lines) — the frontend renders execution as a live state machine.

4. **Device lock races.** Without atomic acquisition, two runs can grab the same device simultaneously. Mobile Hub's `DeviceService.acquireLock()` uses a single atomic `findOneAndUpdate` — no window for a race.

## Data model

### ExecutionRun
```ts
{
  _id,
  machineId: string,            // ref MachineHost — required, indexed
  deviceUdid: string,
  buildId: ref Build | null,    // null if org manages builds externally
  project: string,
  branch: string,
  suite: string,                // test suite name within the automation repo
  triggeredBy: ref User,
  status: 'queued' | 'preparing' | 'running' | 'passed' | 'failed' | 'cancelled',
  stages: [
    {
      name: 'pulling' | 'restoring_cache' | 'installing' | 'execute',
      status: 'pending' | 'running' | 'done' | 'error',
      startedAt: Date | null,
      endedAt: Date | null,
      error: string | null
    }
  ],
  workspacePath: string,        // ~/mobile-hub-executions/workspace/{runId}/
  cacheKey: string | null,      // computed during 'pulling' stage
  logPath: string,              // absolute path to the run log file
  reportPath: string | null,    // absolute path to Allure report dir after execute
  startedAt: Date | null,
  endedAt: Date | null,
  createdAt, updatedAt
}
```

## Execution pipeline

```
Trigger run (POST /api/execution/runs)
  │
  ▼
[queued] — device lock not yet acquired
  │
  ├─ DeviceService.acquireLock() — atomic findOneAndUpdate, lock: null precondition
  │  └─ on failure: stay queued, retry after a short backoff
  │
  ▼
[preparing]
  │
  Stage: pulling
  ├─ git clone --depth 1 <repoUrl> --branch <branch> workspace/{runId}/
  ├─ compute cacheKey = sha256(package.json + lockfile + platform + nodeVersion)
  ├─ stage → done
  │
  Stage: restoring_cache
  ├─ check cache/{cacheKey}/ exists
  ├─ HIT  → symlink cache/{cacheKey}/node_modules → workspace/{runId}/node_modules
  │         stage → done, skip 'installing'
  └─ MISS → stage → done, proceed to 'installing'
  │
  Stage: installing  (skipped on cache hit)
  ├─ npm install in workspace/{runId}/
  ├─ copy node_modules to cache/{cacheKey}/node_modules
  ├─ stage → done
  │
  ▼
[running]
  │
  Stage: execute
  ├─ inject env values from org/project config (encrypted at rest, decrypted at run time)
  ├─ invoke runner: wdio | appium-raw | espresso | xcuitest (per automation.framework)
  ├─ runner writes to logPath (tail via SSE)
  ├─ runner generates Allure output to workspace/{runId}/allure-report/
  ├─ PASS → stage done, ExecutionRun.status = 'passed'
  └─ FAIL → stage error, ExecutionRun.status = 'failed'
  │
  ▼
DeviceService.releaseLock()
Cleanup: workspace/{runId}/ deleted (cache dir kept)
```

Every stage transition pushes a structured event to `/ws/execution/:runId`. Log lines stream separately via SSE.

## Workspace and cache layout

```
~/mobile-hub-executions/
  workspace/
    {runId}/
      (automation repo contents, cloned fresh per run)
      node_modules -> ../../cache/{cacheKey}/node_modules   (symlink on cache hit)
      allure-report/   (generated by test runner)
  cache/
    {cacheKey}/
      node_modules/    (persisted across runs with matching key)
```

The workspace directory is deleted after a run completes (pass, fail, or cancel). The cache directory is never deleted automatically — a separate maintenance task (V2) will purge old cache entries by last-used date.

## Cache key construction

```ts
const cacheKey = sha256([
  fs.readFileSync(path.join(workspacePath, 'package.json'), 'utf8'),
  fs.readFileSync(path.join(workspacePath, 'package-lock.json'), 'utf8'),  // or yarn.lock
  platform,      // 'darwin' | 'linux' | 'win32'
  process.version  // Node version
].join('\n'));
```

All four inputs are required. Using only the lockfile is insufficient — the lockfile may not be committed, or may be regenerated identically after a meaningful change to `package.json`. This was a confirmed collision source in the prior reference implementation.

## propChain baton pattern

Each stage function is a pure async function that receives the accumulated `ExecutionContext` from the previous stage and returns an enriched version. No stage accesses global state — everything is passed through the context object.

```ts
type ExecutionContext = {
  runId: string;
  workspacePath: string;
  cacheKey: string | null;
  cachePath: string | null;
  cacheHit: boolean;
  repoPath: string | null;
  appiumCapabilities: Record<string, unknown> | null;
  logPath: string;
};

// Stage function signature
type StageHandler = (ctx: ExecutionContext) => Promise<ExecutionContext>;

// Orchestrator chains them
async function runPipeline(initialCtx: ExecutionContext, stages: StageHandler[]) {
  let ctx = initialCtx;
  for (const stage of stages) {
    ctx = await stage(ctx);        // throws on error → caught by orchestrator → marks stage 'error'
  }
  return ctx;
}
```

The orchestrator wraps each `stage(ctx)` call in a try/catch:
- On success: update `ExecutionRun.stages[n].status = 'done'`, push WS event, advance.
- On error: update `ExecutionRun.stages[n].status = 'error'`, set `error` field, mark run `'failed'`, push WS event, stop.

## Log streaming — SSE

Execution log tail is delivered via **Server-Sent Events (SSE)**, not WebSocket. Log streaming is server-to-client only — there is no client message needed. SSE is simpler, works over HTTP/1.1, and the browser reconnects automatically.

```
GET /api/execution/runs/:runId/logs/stream
Content-Type: text/event-stream
```

Backend implementation:
1. `ExecutionOrchestrationService` writes runner stdout/stderr to `logPath` (a file in the workspace).
2. A `fs.watch` or `readline` stream on `logPath` feeds new lines into the SSE response.
3. Each log line is sent as an SSE event:
   ```
   event: log
   data: {"line": "INFO Running suite: regression", "ts": "2026-08-21T10:00:01Z"}
   ```
4. When `ExecutionRun.status` reaches a terminal state, a final event is sent and the SSE connection is closed:
   ```
   event: done
   data: {"status": "passed"}
   ```

The existing `/ws/execution/:runId` WebSocket is for **structured stage-transition events only** — not raw log lines. Keeping them separate means the WS message volume stays low and typed.

## Test reports — Allure

The platform assumes **Allure** as the default test report format. After the `execute` stage completes:

1. The runner generates `workspace/{runId}/allure-report/` (configured in the automation repo's Allure config — Mobile Hub does not generate this, only serves it).
2. `ExecutionOrchestrationService` sets `ExecutionRun.reportPath` to the absolute path of the Allure report directory.
3. The report is served as static HTML:
   ```
   GET /api/execution/runs/:runId/report       → redirect to /api/execution/runs/:runId/report/index.html
   GET /api/execution/runs/:runId/report/*     → serve static files from reportPath
   ```

Allure configuration (reporter plugin, result dir) lives in the automation repo — declare it in `wdio.conf.js` or equivalent. The `structure.configFile` key in `mobilehub.project.yaml` tells Mobile Hub where to find it.

## Org/project config integration

The `automation` block in `mobilehub.org.yaml` / `mobilehub.project.yaml` controls what the execution module does:

```yaml
automation:
  framework: wdio          # wdio | appium-raw | espresso | xcuitest
  repoUrl: https://github.com/example/mobile-automation
  branch: main
  structure:
    configFile: wdio.conf.js
    envFile: .env
    testDir: tests/
  env:
    - key: APP_ENV
      value: staging
    - key: API_KEY
      value: encrypted:v1:...    # encrypted at rest in OrgConfig
```

`ConfigService` resolves and merges org + project config before each run. The `env` values are decrypted at run time and injected into the runner process's environment — they are never written to disk or logged.

If `features.execution === false` for an org, all execution endpoints return `403 Feature disabled`.

## ExecutionOrchestrationService responsibilities

| Responsibility | Notes |
|---|---|
| `createRun(params)` | Creates `ExecutionRun` (status: `'queued'`), enqueues |
| `processQueue()` | Picks next queued run, attempts device lock acquisition |
| `runPipeline(runId)` | Executes the propChain: pulling → restoring_cache → installing → execute |
| Stage transition events | Emits a WS event on every stage status change |
| Log file watching | Sets up `fs.watch` on logPath, feeds lines to SSE subscribers |
| `cancelRun(runId)` | Sets status to `'cancelled'`, kills the runner process if running, releases device lock |
| Device lock release | Always called in a `finally` block — runs that crash still release the lock |

## API surface

### REST
```
POST /api/execution/runs              — trigger a run (operator+)
     body: { deviceUdid, project, branch, suite, buildId? }
GET  /api/execution/runs              — list runs (viewer+), filterable by status/project/device
GET  /api/execution/runs/:runId       — get run detail + stage list (viewer+)
POST /api/execution/runs/:runId/cancel — cancel a queued or running run (operator+)
GET  /api/execution/runs/:runId/logs/stream — SSE log tail (viewer+)
GET  /api/execution/runs/:runId/report      — serve Allure report (viewer+)
GET  /api/execution/runs/:runId/report/*    — serve Allure static assets (viewer+)
```

### WebSocket (main API port)
```
WS /ws/execution/:runId?token=<jwt>
```

Events pushed over this channel (stage transitions only — raw logs go via SSE):
```json
{ "type": "stage",  "stage": "installing", "status": "running",  "startedAt": "..." }
{ "type": "stage",  "stage": "installing", "status": "done",     "endedAt": "..."   }
{ "type": "status", "status": "passed",    "endedAt": "..."                          }
{ "type": "stage",  "stage": "execute",    "status": "error",    "error": "wdio exit 1" }
```

## Known issues from reference — and Mobile Hub fixes

| Reference issue | Root cause | Mobile Hub fix |
|---|---|---|
| Two runs acquired the same device simultaneously | Device lock was read-then-write, not atomic | `DeviceService.acquireLock()` uses `findOneAndUpdate` with `lock: null` precondition |
| Cache key collisions on package changes | Cache key used lockfile only | Key includes `package.json` + lockfile + platform + Node version |
| Hardcoded tap automation for app env setup | UI env selection had no config-driven alternative | `automation.env` block in YAML injects env vars at run time — no UI interaction needed |
| Log streaming used WebSocket (bidirectional overhead for one-way data) | WS was already in use; extended for logs | SSE on dedicated endpoint — simpler, auto-reconnects, correct transport for the direction |
| Workspace directories not cleaned up on crash | Cleanup only in success path | Workspace deletion in `finally` block, always runs |
| Device lock not released on orchestrator crash | Release only in success path | Lock release in `finally` block inside `runPipeline` |
