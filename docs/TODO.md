### auth — ✅ tested (2026-08-22, re-verified same day after refactor onto `fastify-auth-kit`)
- [x] `user.model.ts` — email/name/passwordHash/role (`viewer`/`operator`/`admin`) — unchanged, mobile-hub-owned
- [x] **Refactored onto [`fastify-auth-kit`](https://github.com/deepak-rk/fastify-auth-kit)** (extracted personal package, installed via `npm install github:deepak-rk/fastify-auth-kit`): `auth.service.ts` now just implements the package's `AuthUserStore<IUser, UserRole>` interface (argon2 hashing, first-user-is-admin policy, `DuplicateUserError` on E11000 — all mobile-hub's own business logic, the package has no opinion on any of it). `auth.routes.ts` and `common/middleware/auth.ts` are **deleted** — `POST /register`, `POST /login`, `GET /me`, `app.authenticate`, `app.requireRole` all now come from the package, wired up in `app.ts`.
- [x] JWT payload is now just `{sub, role}` (package's `JwtPayload` shape) — dropped the redundant `email` field that used to also be embedded in the token; `/me` still returns email via a DB lookup.
- [x] Smoke-tested full flow again post-refactor: register → login → `/me` with/without token → duplicate email 409 → devices lock/unlock (which read `req.user.sub`/`req.user.role`) → `GET /api/config` (admin-only) — all still correct.
- [x] JWT expiry: `expiresIn: '24h'`, configured via the package's `AuthRoutesOptions`.
- [ ] The backend is CommonJS; `fastify-auth-kit` is ESM-only, so the package is loaded via dynamic `await import('fastify-auth-kit')` in `app.ts`/`auth.service.ts` rather than a static import — see `docs/LESSONS.md`. Works correctly but is a real bit of accumulated complexity; a full ESM migration of the backend (which backend/CLAUDE.md's "Intended stack" already nominally prefers) would remove the need for this. Not done this pass — out of scope for "consume the package," flagged as a real follow-up.
- [x] **Independent, tighter rate limit on `/register`/`/login` (2026-08-27)** — `common/auth-rate-limit.ts`, config-driven (`AUTH_RATE_LIMIT_MAX` default 20/min, `AUTH_RATE_LIMIT_WINDOW_MS` default 60000). Not built on `@fastify/rate-limit`'s own `app.rateLimit()` decorator — that silently never fires here, since its returned preHandler shares a per-request guard flag with the check the plugin's global registration already auto-attaches to every route; confirmed live (12 attempts, zero 429s) before building a small self-contained fixed-window limiter instead. `GET /me` deliberately excluded — not brute-forceable (needs an already-valid JWT) and called on every page load. Verified live: 5 real attempts through, 6th+ get 429, an unrelated route unaffected in the same window. 5 new unit tests. **Known limitation**: the in-memory hit-tracking `Map` never evicts expired entries, so it grows by one entry per unique IP ever seen, for the process lifetime — fine at lab scale, would need an eviction pass or a bound before this app is ever internet-facing.
- [ ] No password reset / email verification flow (fine for v1, note for later)
- [ ] No refresh-token flow — a token just stops working after 24h, user re-logs-in. Acceptable for v1, revisit if session length becomes a complaint.
- [ ] Zero `.test.ts` unit tests for this module specifically (it has been smoke-tested via curl, which is real coverage, but nothing runs in `npm test`) — the decorator/route *logic itself* now has real test coverage in `fastify-auth-kit`'s own repo, just not mobile-hub's specific `AuthUserStore` wiring

## P0 correctness round — 2026-08-29 (all live-verified)

Driven by two external gap reviews (see "Spec & reference drift" below for the audit that preceded them). Every claim here was checked against a running system, not inferred.

- [x] **`common/process-supervisor.ts` (new)** — one place child processes are launched, supervised and killed, created because the same failure class had recurred across execution, streaming and scripts. Owns: Windows executable resolution, explicit stdio, pid tracking, process-**tree** cancellation, timeouts, and outcome normalization. **13 unit tests** using real child processes.
  - Fixes **`spawn('npm')` → ENOENT on Windows**: resolves `npm` → `npm.cmd` via PATHEXT rather than `shell: true` (which was tried, reverted, and is documented as wrong — it breaks cancellation, since the signal hits the wrapping shell and the real grandchild survives). Verified live: `resolveExecutable('npm')` → `C:\Program Files\nodejs\npm.cmd`, and a full execution run with plain `setup: npm ci` / `run: npm run typecheck` **passed all four stages** with no `cmd /c` workaround.
  - Fixes **a stage hanging on `'running'` forever**: a spawn failure is now a `RunOutcome` (`spawn-failed`), not a thrown exception, so every path reaches the stage update. Previously only the nonzero-exit path did.
  - Cancellation now kills the whole tree (`taskkill /T` on Windows, process-group kill on POSIX) — a test runner is `npm → node → wdio → …`, and orphaning the tail leaves a process still holding a device.
  - Child env is **not** inherited by default; callers opt in. Pinned by a test, because a child inheriting the hub's full environment is how secrets reach a crash log — an observed failure mode in this workspace, not a hypothetical.
- [x] **Durable artifacts split from the ephemeral workspace** — new `EXECUTION_ARTIFACTS_DIR` (default `~/mobile-hub-artifacts`) holds `run.log` (and later Allure) at `artifactsPath`; `EXECUTIONS_DIR` keeps only the clone/`node_modules` and is now **deleted in `finally`**. Verified live: workspace gone after the run, `run.log` intact at 4147 bytes.
- [x] **`GET /api/execution/:id/logs`** — serves the stored log. The frontend falls back to it whenever the WS stream isn't live, so a finished run finally shows its output instead of "Waiting for output…" forever. Verified live against a real completed run.

A device-locked rejection is `precondition`, a backend restart or spawn/clone failure is `infra`, only a nonzero exit from the `execute` stage is `test`. **Analytics now computes pass rate over attributable runs only**, so lab contention can no longer make a healthy suite look unstable; totals still count everything, so lab problems stay visible.
